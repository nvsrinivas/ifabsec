# GPU runs: 2026-11-21, RTX 4090

Two runs of the SGLang patch, the checks, the attacks and the latency
benchmark on real hardware, the same day on two fresh pods with the same
setup. Numbers are transcribed from the pods' terminal output. The second
run's results are at the end; where they change the reading of the first,
that section says so.

## Setup

| | |
|---|---|
| GPU | 1× NVIDIA RTX 4090, 24 GB (RunPod, driver 595.112.07, CUDA 13.2) |
| Model | Qwen/Qwen3-8B |
| SGLang | `efab9d61` (0.5.24.dev2028), built without Rust extensions |
| Patch | `engine/sglang/ifabsec-sglang.patch` as of PR #6, covering `RadixCache` and `UnifiedRadixCache` |
| Server flags | `--enable-cache-report`, otherwise defaults |

| Tenants | Synthetic. Alice and Bob in org `acme`; Eve in `acme` for the attacks, in `beta` for one check |

## Attacks (`attack/run_pod.py`)

Eve is in the same org as Alice, sharing the org system prompt. K = 20
candidates; 10 guessing trials, 5 extraction trials.

| | Stock | Labels | Chance |
|---|---|---|---|
| Extract a 6-digit account number from cached-token counts | **6 of 6 digits, every trial** | **0 digits** | — |
| Guess the account among 20, cached-token channel | 0.7 | 0.1 | 0.05 |
| Guess the account among 20, timing channel | 0.6 | 0.0 | 0.05 |
| Median latency gap, right vs wrong guess | **41.85 ms** | −0.29 ms | — |

## Reading the numbers

- **Stock SGLang leaks, and the leak is practical.** A same-org co-tenant
  recovered the full account number digit by digit in every trial. The 42 ms
  timing gap is large enough to exploit without cached-token reporting.
- **Labels close the channel and keep legitimate sharing.** Eve recovers
  nothing; the timing gap disappears; 0.1 on the guess is one coin-flip hit
  in ten trials, consistent with chance. Alice's own hits and the shared org
  prompt still work.
- **Stock guessing at 0.6–0.7 rather than about 1.0 is a limit of the test
  setup, not of the attack.** One trial is Alice's ~600-token prompt plus 20
  probes of ~600 tokens each, about 12,600 tokens against a 6,860-token
  cache, so Alice's entry is evicted partway through the trial. Flushing
  between trials (second run) didn't change it, which rules out eviction
  *across* trials. Digit extraction uses far fewer tokens and succeeded every
  time.

## Second run

A fresh pod, the same setup, with the harness flushing the cache before each
attack trial, the latency benchmark, and the input-identity checks.

### Checks

All sharing and rejection checks passed again (Alice 52 of 53, Bob 18, Eve 0,
requests without a token and client salts rejected, `/generate` isolated,
0 boundary fallbacks). Overhead for short single requests: 22.5 ms with
labels vs 22.3 ms stock.

| Input identity | Result |
|---|---|
| Prompt token ids, labeled vs stock | PASS, identical (53 vs 53) |
| Prompt length and 48-token greedy output, both caches empty | PASS, 36 vs 36 tokens, identical output |

Before the cache was emptied for the second comparison, the outputs differed
with equal prompt lengths. The two servers had different amounts of that
prompt cached, and a cached prefix changes the floating-point path enough to
change a long greedy output. With both caches empty they match.

(One check failed in the rerun of `check.py`, Alice's repeat at 18 of 53, and
it was the test's own fault: the identity comparison's cache flush ran between
Alice's two requests. The identity check now runs first.)

### Latency under multi-tenant load (`bench/latency.py`)

4 orgs × 16 users, a ~1.5K-token system prompt per org, two-turn sessions with
~150-token messages, 16 sessions in flight, 32 output tokens per request,
128 requests per policy.

| Policy | Hit rate | TTFT p50 | TTFT p95 | End-to-end p50 | Requests/s | Prompt tokens computed |
|---|---|---|---|---|---|---|
| Stock (leaks) | 82.6% | 603 ms | 1,350 ms | 1,305 ms | 11.74 | 29,210 |
| Per-user `cache_salt` (safe) | 0.0% | 2,983 ms | 3,934 ms | 3,570 ms | 3.90 | 167,859 |
| Labels (safe) | 82.1% | 673 ms | 1,471 ms | 1,397 ms | 11.56 | 30,093 |

- **Labels keep stock's efficiency safely:** 4.4× faster first token and 3×
  the throughput of per-user isolation, and within 2% of stock's throughput.
- **The size of that gap comes from the tiny cache.** Per-user isolation keeps
  a copy of the org prompt per user: 16 sessions in flight need about 28K
  tokens against 6,860, so every entry is evicted before reuse (0% hits, even
  on a user's own second turn). Labels keep one copy per org, about 6K tokens
  for 4 orgs. On a GPU with much more KV cache, per-user isolation would get
  some hits back and the gap would narrow; the memory ratio (copies per user
  vs per org) would not.
- **Labels' first token is about 70 ms (12%) slower than stock** at the
  median, with throughput within 2%. Likely the extra work at the chat
  endpoint per request (signature check, an extra chat-template render and
  tokenization), possibly run-to-run variation between server starts. Not
  yet profiled.
