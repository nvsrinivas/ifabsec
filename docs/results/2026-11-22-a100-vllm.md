# A100 PCIe 80GB, vLLM, 2026-11-22

RunPod A100 PCIe 80GB, vLLM v0.34.0 (torch 2.14.0+cu130) with
`engine/vllm/ifabsec-vllm.patch`, installed by `scripts/pod/setup-vllm.sh`
into its own environment. Model: Qwen/Qwen3-8B. Run with
`ENGINE=vllm MODELS=Qwen/Qwen3-8B bash scripts/pod/suite.sh`; the benchmark
and its observe policy were rerun after two fixes (below). Attacks run only
against a server set up for testing, with synthetic secrets. Raw output:
[`raw/vllm-a100/`](raw/vllm-a100/).

Server flags: `--enable-prefix-caching --enable-prompt-tokens-details
--block-size 16 --prefix-match-unit 16 --enable-auto-tool-choice
--tool-call-parser hermes`. 16-token blocks are the finest granularity vLLM
offers, so the most an attacker can learn per probe; with the default on this
GPU, the checks' 53-token prompts filled no block at all.

## Correctness checks

All 15 pass ([`check.txt`](raw/vllm-a100/check.txt)). On stock vLLM a second
sender of identical text hits 48 of 53 tokens (three full blocks). With labels:

- model input and 48-token greedy output identical to stock;
- Alice's resend hits 48 of 53; Bob (same org, identical text) hits 16, the
  one full block of the 18-token org prompt; Eve (other org) hits 0;
- requests without a token or with a client-chosen `cache_salt` get HTTP 400;
  `/v1/completions` without a token shares nothing;
- approved tool schemas are shared (144 of the 155-token org prompt plus
  tools), unapproved ones are not, altered ones are rejected;
- no "isolating request" warnings: boundaries are stable for Qwen's template.

The user-tag alternative (an opaque tag before the first user message) makes
the same prompt 45 tokens instead of 36 and changes the 48-token greedy
output. One prompt; it shows the tag changes what the model reads, not that
the answer gets worse.

## Attacks

10 guessing trials (20 candidates each), 5 extraction trials per mode.

| policy | guess accuracy (cached-token / timing) | timing gap | extraction, digit by digit | extraction, digit groups ≤3 |
|---|---|---|---|---|
| stock | 1.0 / 1.0 | 31.03 ms | 0 of 6 | 0 of 6 (1,110 probes per trial) |
| labels | 0.0 / 0.1 | 0.52 ms | 0 of 6 | 0 of 6 |

Chance is 0.05; 0.1 is one hit in ten trials.

Guessing breaks stock vLLM completely and is at chance with labels.

Extraction failed on stock vLLM too, unlike SGLang (6 of 6 digits). vLLM
reports cached tokens in whole blocks, so one guessed digit moves the count
only when it completes a 16-token block. Eve's group attack tries every
1-, 2- and 3-digit continuation; in all five trials the next block boundary
needed more digits at once than that. Block granularity is an accidental,
partial defense: it makes reading out a short secret expensive (10× per
digit guessed together), not impossible, and it does nothing against
confirming a guess from a list, which is the attack that worked here.

`labels_shared` (every message labeled org-wide) tracks `labels` within a
point or two; see the raw file.

- **Labels keep the sharing.** Hit rate within 0.6 points of stock at every
  size. Per-user salt prefills 5× more tokens at 256 users and keeps 43% of
  stock throughput.
- **Labels cost 6–8% of throughput on vLLM**, more than on SGLang (about 2%).
- **The cost is the ingress checks, not the scoped keys.** `observe` runs
  every check but keys the cache like stock, and is already 4–8% below stock;
  scoped keys add 0–3% more. The labeled server's profile: ingress 2.66 ms per
  request in the API server (boundary finding 1.48 ms, token verification
  0.57 ms); in the engine core, 14 µs per block-key call and 0.64 ms once per
  request to unseal the internal salt. vLLM's API server handles every
  request on one asyncio event loop, so per-request CPU there delays the
  requests behind it. Caching boundary renders per approved prompt and moving
  verification off the event loop are the obvious next steps.
- **The user tag is cheapest (96–99%)** because it checks nothing. It pays
  differently: the model reads the tag (see above), and the engine trusts
  whoever writes it.

Server-to-server variation: `observe` ran on a different server start from
the other policies, so differences of a point or two are within noise.

## Fixes found on the pod

- vLLM must be started with its `vllm` console script; under
  `python -m vllm.entrypoints.cli.main`, worker processes re-import the main
  module and torch asserts "duplicate template name".
- pip-installing vLLM over an image's torch left stale files and the same
  assertion; `setup-vllm.sh` now installs into its own uv environment.
- vLLM rejects `/` in client `cache_salt`; the per-user policy uses `org.user`.
- `observe` first keyed the cache on the sealed salt (unique per request,
  0% hits); it now keys like stock with no salt.
