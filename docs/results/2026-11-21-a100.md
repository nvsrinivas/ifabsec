# A100 PCIe 80GB, 2026-11-21

RunPod A100 PCIe 80GB, SGLang pinned at `efab9d61`, `scripts/pod/suite.sh`.
Models: Qwen/Qwen3-8B (main), microsoft/Phi-4-mini-instruct (second template
family). Attacks run only against our own server with synthetic secrets.
Trials: 10 guessing trials (20 candidates each) and 5 extraction trials per
mode (`attack/run_pod.py` defaults).

At 16 users all policies are similar. Per-user isolation prefills ~347K
tokens at 256 users vs ~77K for labels, and halves throughput.

Labels match stock on hit rate and throughput, but first tokens are ~90 ms
slower at p50 with 256 users. The labeled server's profile shows
ingress ≈ 4.0 ms per request (verify 2.5 ms, boundary 1.2 ms, wall time),
too small by itself to explain 90 ms; the suspect is contention for the GIL
in the HTTP process with the streaming event loop. `IFAB_MODE=observe`
(PR #12) separates ingress cost from scoped-key cost; results below.

## Observe-mode split

`python bench/latency.py --users 256 --repeat 2` on overhead-2 (PR #12):
256 users per org × 4 orgs = 1,024 users, concurrency 16, two rounds averaged.
This is a heavier load point than the tables above (64 per org), so the two
are not directly comparable.

| policy | hit rate | req/s | TTFT p50 | TTFT p95 | prefill tok |
|---|---|---|---|---|---|
| stock | 90.6% | 25.6 | 166 ms | 210 ms | 253K |
| observe | 90.5% | 25.3 | 175 ms | 215 ms | 256K |
| labels | 90.4% | 24.9 | 195 ms | 222 ms | 259K |
| labels_shared | 89.2% | 23.9 | 203 ms | 271 ms | 290K |
| per_user | 48.3% | 12.5 | 213 ms | 1,477 ms | 1,389K |

- stock → observe, +8 ms p50: the cost of verifying the token and computing
  boundaries in the HTTP process.
- observe → labels, +20 ms p50: the cost of scoped keys in the scheduler.
- Labels vs per-user isolation: 2× throughput, 5.4× less prefill, and p95
  TTFT 222 ms vs 1,477 ms.
- Profile (HTTP process): ingress 5.3 ms wall but 2.4 ms CPU; boundary 2.4 ms
  wall, 1.6 ms CPU. About half the ingress wall time is waiting for the GIL
  or the thread pool, not work.

### Scheduler profile (labels only, one round, 1,024 users)

Labels alone: 90.3% hit, 25.3 req/s, TTFT p50 183 ms, p95 216 ms
(stock above: 166 / 210 ms, 25.6 req/s).

- Scheduler: 94 µs per call (unseal 29 µs, pack 51 µs), about 5 calls per
  request, so roughly 0.5 ms of scheduler time per request. The scoped keys
  are not where the latency goes.
- HTTP process: ingress 2.2 ms wall / 0.7 ms CPU; verify 1.8 ms wall / 0.4 ms
  CPU. Boundary is 20 µs here because labels only render the org system
  prompt, which repeats; the 2.4 ms earlier came from labels_shared, which
  renders every message.
- The earlier observe → labels gap (+20 ms) is within the round-to-round
  spread (labels was 200 ms and 189 ms in the two rounds; 183 ms here).

Net, across the three labeled runs at this load (200, 189 and 183 ms):
labels cost about 25 ms at p50 (17–34 ms, 10–20%), ~5% at p95, and ~2% of
throughput. What remains is mostly the HTTP process waiting for
the GIL around token verification, not computation.
